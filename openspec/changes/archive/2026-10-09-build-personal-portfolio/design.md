## Context

См. proposal.md, раздел Why. В проекте минимальная страница Astro, пустая конфигурация, TypeScript strict и зависимость astro ^7.3.8. Готовых компонентов, коллекций, статей и общих стилей нет. Пользователь предоставил структуру каталогов, палитру и макет страницы «Обо мне».

Документ необходим: изменение затрагивает все страницы, вводит модель публикаций и две зависимости. Официальная документация, проверенная при исследовании:
- https://docs.astro.build/en/guides/content-collections/
- https://docs.astro.build/en/guides/routing/
- https://docs.astro.build/en/recipes/rss/
- https://docs.astro.build/en/guides/integrations-guide/sitemap/

## Goals / Non-Goals

**Goals:**
- Разделить общую разметку, содержание страниц и правила публикации.
- Получать страницы статей и RSS из одного набора опубликованных записей.
- Сохранять читаемость на мобильном и возможность пользоваться сайтом без клиентского JavaScript.

**Non-Goals:**
- Серверный рендеринг, клиентский роутер, редактор статей, поиск и пагинация.
- Автоматический деплой и публикация статей по расписанию.
- Создание вымышленных биографических данных, проектов и готовых авторских статей.

## Decisions

### 1. Статическая сборка и обычные Astro-компоненты

Сохранить статический вывод Astro и навигацию обычными ссылками. BaseLayout оборачивает страницы и содержит Header, main и Footer. Отдельный layout статьи на старте не требуется: динамическая страница использует BaseLayout.

Альтернатива: SSR или React. У контента нет необходимости обновляться при каждом запросе, поэтому эти зависимости и runtime усложняют поддержку без пользы.

Порядок реализации сохраняет запрос пользователя: BaseLayout → Header → Footer → «Обо мне» → «Работы» → «Статьи» → «Контакты» → завершение публикационного контура.

### 2. Единая конфигурация сайта

Добавить src/config.ts: имя, описание, предполагаемый URL https://webreznov.site, GitHub https://github.com/MaximRemizovFEdev, необязательные email и Telegram. GitHub взят из ссылки на репозиторий; email и Telegram не угадывать. Основной URL импортировать в astro.config.mjs как site; SEO и RSS используют это же значение.

Пока email или Telegram не предоставлены, соответствующие ссылки не выводить; не создавать href="#" и фиктивные адреса. После заполнения конфигурации ссылки появляются и в footer, и на странице контактов. Для footer добавить навигацию из макета и текущий год сборки.

Альтернатива: повторять контакты в нескольких компонентах. Единый источник исключает расхождения и позволяет внести уточнения без изменения архитектуры.

### 3. Дизайн: два размера текста и композиция макета

В global.css определить переменные цветов: фон #0D0F12, текст #F5F5F5, вторичный #9CA3AF, акцент #60A5FA; цвет линий — отдельная приглушённая переменная. Контейнер до 960px с боковыми отступами. Системный sans-serif, без внешних шрифтов и анимаций.

Приоритет отдаётся прямому требованию о двух размерах: основной текст 18px, все заголовки 36px; на узких экранах соответственно 16px и 28px. Подписи и даты имеют основной размер, различаются цветом. Семантические h1/h2/h3 сохраняются даже при одинаковом визуальном размере. Код использует системный monospace с размером основного текста.

Сохранить композицию изображения: верхнее меню, акцентное «веб-приложения», разделённые линиями секции, две колонки специализации, история работы с датами, нижняя навигация. Не фиксировать переносы заголовка по координатам скриншота. На ширине около 720px колонки складываются, даты истории идут перед описанием; четыре ссылки меню остаются доступны без JS.

Альтернатива: несколько размеров заголовков ради точного воспроизведения картинки. Она противоречит явному текстовому требованию; размеры можно пересмотреть при ревью.

### 4. Содержание и неизвестные данные

Страница «Обо мне» использует текст предоставленного макета, включая IBS (проект Сбер), Sarax, Grindata, EPAM и сервис «Ай да сказка». Не расширять биографию неподтверждёнными сведениями.

«Работы» начинает с подтверждённого макетом проекта «Ай да сказка» как текстовой записи; URL, детали роли и технологический стек добавляются только при наличии данных. История работодателей не становится автоматически списком публичных проектов.

Три указанных имени Markdown-файлов использовать как явно помеченные заготовки с draft: true, если пользователь не предоставит готовые тексты. Дата в шаблоне служит примером метаданных и должна быть проверена при публикации. Пустой публичный список статей показывает короткое сообщение и ссылку на RSS. Контакты всегда включают известный GitHub; неизвестные каналы скрыты до заполнения.

Альтернатива: сгенерировать статьи и описания проектов от имени автора. Это создаёт недостоверный публичный контент и не требуется для проверки механизма публикации.

### 5. Коллекция и единые правила отбора

В src/content.config.ts определить blog через defineCollection, glob из astro/loaders для плоской папки src/content/blog/*.md и Zod из astro/zod, соответствуя актуальному API. Проверять title и description как непустые строки, pubDate как дату, updatedDate как необязательную дату, draft как boolean с default false.

Идентификатор — URL-совместимое имя Markdown-файла без расширения; использовать плоские имена в kebab-case, не вводить отдельное редактируемое поле slug. Маршрут src/pages/articles/[id].astro генерирует getStaticPaths и вызывает render для содержимого.

В небольшом src/lib/blog.ts сосредоточить получение опубликованных записей, сортировку pubDate по убыванию с id как стабильным вторичным ключом и построение ссылки на статью. Список, getStaticPaths и RSS используют этот источник. Черновики исключаются как в production, так и из публичных маршрутов dev; редактировать их можно в Markdown. Автопубликация по дате отсутствует: draft управляет видимостью, pubDate — сортировкой и метаданными.

Альтернатива: независимая фильтрация в каждом месте. Она допускает появление черновика в RSS или маршрутах при его отсутствии в списке.

### 6. SEO, RSS и sitemap

BaseLayout принимает title и description, формирует уникальные title, canonical без query/hash, базовые Open Graph с og:type website или article и язык ru. Для статьи используются её метаданные и дата; при наличии updatedDate выводить её отдельно. og:image добавлять только при наличии реального изображения. В head подключить SVG favicon, RSS alternate и sitemap.

Добавить совместимые версии @astrojs/rss и @astrojs/sitemap с обновлением lockfile, без смены основной версии Astro. Endpoint src/pages/rss.xml.ts создаёт статический RSS с заголовком, описанием, языком ru, датой и абсолютной ссылкой для каждой публикации. Полный HTML статьи в RSS на старте не включать.

Sitemap строится официальной интеграцией по сгенерированным страницам; у черновиков нет маршрутов, поэтому нет и записей sitemap. Добавить public/robots.txt с ссылкой на sitemap-index.xml.

Альтернатива: самостоятельно сериализовать RSS и XML sitemap. Официальные пакеты обеспечивают корректную XML-сериализацию и уменьшают объём собственного кода.

## Risks / Trade-offs

- [Макет использует больше размеров текста] → Следовать двум токенам; явно вынести решение на ревью предложения.
- [Нет email, Telegram, полных данных проектов и текстов статей] → Не выводить вымышленные ссылки, сохранить заготовки как черновики; заполнение не меняет архитектуру.
- [Основной домен пока предполагается] → Централизовать site и проверить canonical, RSS и robots.txt перед публикацией.
- [Новая статья не появляется на работающем сайте сразу после редактирования файла] → Публикация обновлённого результата сборки и CI/CD остаются вне этого изменения.
- [Переименование Markdown меняет URL] → Документировать стабильность имени файла; перенаправления не входят в первый выпуск.
- [Длинные фрагменты Markdown ломают мобильную сетку] → Переносить ссылки, ограничивать ширину контента, прокручивать pre и широкие таблицы внутри статьи.

## Migration Plan

1. Реализовать компоненты и страницы в рабочем дереве, сохраняя существующие изменения пользователя.
2. Добавить коллекцию, RSS и sitemap, заполнить только подтверждённые данные.
4. До фактической публикации подтвердить домен, контакты и готовность контента. Сам деплой выполняется отдельной задачей.
5. При необходимости откатить это изменение средствами Git после его отдельного коммита; не сбрасывать несвязанные пользовательские изменения.
