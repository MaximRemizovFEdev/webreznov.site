# HTA: приложение для Windows из обычного HTML — теория и семь практических применений

Иногда нужна небольшая программа: выбрать папку, заполнить несколько полей, нажать кнопку и получить результат. Писать полноценное десктопное приложение ради такой задачи кажется избыточным. Консольный скрипт решает проблему, но пользоваться им удобно не всем.

У Windows есть любопытный механизм для подобных случаев — HTA, или HTML Application. Он позволяет сделать интерфейс на HTML и CSS, добавить скрипты и запускать получившийся файл в отдельном окне. Технология старая, со своими ограничениями, однако знакомство с ней полезно: это наглядный пример того, как веб-интерфейс может управлять локальными операциями.

## Что такое HTA

HTA — HTML-приложение, которое выполняется специальной программой `mshta.exe`. Разметка отвечает за интерфейс, стили — за оформление, скрипты — за поведение. Обычно всё помещается в файл с расширением `.hta`, хотя стили, изображения и код можно хранить отдельно.

В основе находится инфраструктура Internet Explorer. Поэтому ожидать возможностей актуального Chrome или Edge нельзя: совместимость CSS, JavaScript и браузерных API ограничена старым движком и выбранным режимом документа.

При этом HTA отличается от страницы, открытой в браузере. Через COM-объекты приложение может обращаться к файлам, запускать программы и взаимодействовать с установленными компонентами Windows. Эти возможности зависят от доступных компонентов и прав пользователя. Само расширение `.hta` прав администратора не предоставляет.

В документации Microsoft описаны отдельные настройки окна: заголовок, рамка, иконка, кнопки сворачивания и разворачивания. Для них используется элемент `HTA:APPLICATION`.

## Первое приложение

Создадим файл `hello.hta` и сохраним его в UTF-8:

```html
<!DOCTYPE html>
<html>
<head>
  <meta http-equiv="X-UA-Compatible" content="IE=9">
  <meta http-equiv="Content-Type" content="text/html; charset=utf-8">
  <title>Мой инструмент</title>
  <HTA:APPLICATION
    APPLICATIONNAME="HelloHTA"
    BORDER="thin"
    MAXIMIZEBUTTON="no"
  >
  <style>
    body { font: 16px Arial; padding: 24px; }
    input, button { font: inherit; padding: 8px; }
  </style>
  <script type="text/javascript">
    function greet() {
      var name = document.getElementById('name').value;
      alert('Привет, ' + (name || 'разработчик') + '!');
    }
  </script>
</head>
<body>
  <h1>Первое HTA-приложение</h1>
  <input id="name" type="text" value="Максим">
  <button onclick="greet()">Поздороваться</button>
</body>
</html>
```

Если ассоциация файлов настроена и запуск разрешён, файл откроется двойным щелчком. Другой вариант — вызвать его из командной строки:

```bat
mshta.exe "C:\Tools\hello.hta"
```

Здесь намеренно используются простой CSS, `var` и обычные функции. Мета-тег выбирает режим совместимости, но не превращает HTA в современный браузер. Перенести сюда готовую React-сборку простым переименованием файла обычно не получится.

Такой пример показывает только интерфейс. Практическая ценность появляется, когда кнопки связываются с локальными действиями. Ниже — семь сценариев, для которых можно спроектировать подобный инструмент.

## 1. Подготовка папок нового проекта

Допустим, для каждого заказа создаётся одинаковая структура: исходники, материалы клиента, документы и результат. Каждый раз собирать её вручную неудобно, особенно если соглашения об именах регулярно нарушаются.

HTA может предложить форму с названием клиента, номером заказа и базовой директорией. После подтверждения приложение создаст подпапки, скопирует шаблон задания и покажет путь к результату. Для файловых операций подходит `Scripting.FileSystemObject`.

Полезное дополнение — предварительный просмотр структуры. Пользователь сначала видит будущие пути, затем подтверждает создание. Если папка уже существует, программа предлагает другое имя. Получается небольшой помощник, который стандартизирует начало работы и уменьшает количество ручных действий.

## 2. Понятная оболочка для готового скрипта

У разработчика уже может быть PowerShell-скрипт, который собирает архив проекта или обрабатывает изображения. Проблема возникает при передаче инструмента человеку, которому неудобно вводить параметры в терминале.

В HTA можно вынести эти параметры в поля: исходная папка, папка результата, режим обработки. Кнопка запуска вызывает заранее определённый скрипт через `WScript.Shell`, а интерфейс сообщает о начале операции и её завершении.

Для результата важно учитывать код возврата и вывод процесса. Сам факт запуска ещё не означает успех. Длительную обработку лучше организовать так, чтобы окно не зависало: например, отдельный процесс записывает статус в файл, который интерфейс периодически читает. Пути и аргументы требуют проверки и корректного экранирования.

## 3. Генератор документов по шаблону

Представим повторяющуюся задачу: подготовить сопроводительный лист к заказу. Меняются имя клиента, состав работ, дата и примечание, а оформление остаётся одинаковым.

HTA собирает данные через форму, подставляет их в шаблон и сохраняет документ. Для простого результата достаточно HTML или текста. Если нужен документ Word со сложным форматированием, можно рассмотреть автоматизацию установленного Word через COM. Это отдельная зависимость, которую придётся учитывать на компьютере пользователя.

Например, мастерская может формировать карточку ремонта с перечнем оборудования и описанием неисправности. Перед сохранением приложение показывает предпросмотр и проверяет обязательные поля. Значения, вставляемые в HTML, нужно экранировать, чтобы пользовательский текст не менял разметку документа.

## 4. Проверка и преобразование CSV

Небольшой компании регулярно присылают таблицы, которые приходится приводить к одному формату: менять порядок колонок, очищать пробелы, проверять обязательные значения и находить повторы.

HTA может стать локальным инструментом подготовки таких данных. Пользователь указывает файл, выбирает преобразования и получает отдельный результат вместе с отчётом: сколько записей прочитано, какие строки требуют внимания, где обнаружены дубликаты.

Здесь важно не свести обработку CSV к `split(',')`: разделители и переводы строк встречаются внутри кавычек. Нужен корректный парсер, совместимый с используемым движком, либо отдельный обработчик. Стоит также явно выбирать кодировку. Исходный файл лучше сохранять: так результат можно сравнить и исправить настройки без потери данных.

## 5. Локальный просмотрщик отчётов и журналов

Предположим, программа сохраняет журналы в текстовые файлы. Искать сообщения вручную можно, но повторяющаяся диагностика быстро превращается в последовательность одинаковых действий.

HTA позволяет сделать окно с выбором журнала, фильтром по уровню ошибки, поиском и таблицей результатов. Для первой версии достаточно читать ограниченный объём данных и обновлять его по кнопке. После этого можно добавить группировку одинаковых сообщений и экспорт выбранных строк.

Такой инструмент полезен человеку, которому нужно увидеть конкретную проблему, а не изучать весь лог. При этом большие файлы нельзя бездумно загружать целиком: чтение и построение таблицы могут надолго занять интерфейс. Текст журнала следует выводить как текст, без интерпретации HTML.

## 6. Панель повседневных инструментов

Когда рабочий процесс распределён между несколькими папками, программами и инструкциями, можно собрать единую стартовую панель. Например: открыть каталог заказов, запустить редактор, перейти к документации и подготовить резервную копию материалов.

Технически это набор кнопок с заранее заданными действиями. Польза появляется за счёт понятных названий и контекста: рядом можно показать описание операции, расположение файлов и время последнего успешного выполнения.

Для небольшой команды такая панель уменьшает зависимость от устных инструкций. Однако она не становится системой управления доступом: права по-прежнему определяет Windows. Кнопка резервного копирования должна сообщать, куда сохраняются данные и завершилось ли копирование успешно. Наличие кнопки само по себе ещё не гарантирует сохранность файлов.

## 7. Прототип мастера для внутреннего процесса

Иногда сначала нужно проверить сценарий: какие поля требуются сотруднику, в каком порядке задавать вопросы, где показывать ошибки. Полноценная интеграция на этом этапе может быть преждевременной.

В HTA можно собрать пошаговый мастер: выбрать тип заявки, заполнить данные, проверить итог и сохранить результат локально. Для испытания достаточно нескольких экранов и тестовых данных. Сотрудник проходит реальный маршрут, а разработчик наблюдает, где возникают вопросы.

После проверки сценария интерфейс можно реализовать на другой платформе. При этом полезно заранее разделить разметку, проверку данных и системные операции. Тогда прототип останется понятным, даже если временный инструмент придётся поддерживать дольше ожидаемого.

## Ограничения, которые влияют на выбор

Главное ограничение HTA — привязка к старой Windows-инфраструктуре. Современные библиотеки, новые возможности JavaScript и привычные инструменты отладки нельзя считать доступными по умолчанию. Проверять нужно именно целевой компьютер, а не только HTML-страницу в браузере.

Дополнительно запуск может блокироваться политиками безопасности. Microsoft прямо описывает ограничения `mshta.exe` при использовании App Control. Поэтому перед разработкой для организации стоит выяснить, разрешена ли такая технология в её окружении.

Доступ к системе означает и ответственность: HTA следует воспринимать как исполняемую программу. Не стоит подключать непроверенные удалённые скрипты или формировать команды из произвольного ввода. Для локальных данных нужны понятные правила сохранения, проверки и обработки ошибок.

Я бы рассматривал HTA для небольшого инструмента под известное Windows-окружение, особенно если уже существует подходящий скрипт. Для приложения с долгим сроком жизни, современным интерфейсом и широкой аудиторией сначала оценил бы другие способы разработки. Ценность HTA сегодня — в возможности быстро связать простую форму с конкретной локальной задачей.
